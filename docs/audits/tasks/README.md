# 内部 Issue 看板

本目录是仓库内的公共任务池，承接业务组产生的任务和用户直接提出的独立任务。每份任务文件是一张 issue；本页展示未关闭 issue；[`archive/`](archive/) 保存关闭记录。业务组维护长期方向与验收口径，见 [`../README.md`](../README.md)。

**任务文件是状态与交付合同的权威，本表是同步索引。** 协调者在共享工作树即时同步两处，`just docs-check` 校验一致性；状态可见与认领生效不依赖 Git 提交。默认一项完成的任务一个交付 commit，认领、进度、阻塞、释放和例行归档不单独提交。文件名是稳定 issue ID，关闭后仍可引用；不重复使用已归档 ID。

## 用户怎么交办

- “这个问题直接修”：当前会话调查、修改和验证，不强制建 issue 或归业务组。
- “记个任务，让其他 Agent 修”：主会话按下方发布规则建立任务，业务组外的问题作为独立任务进入同一看板。
- 执行会话“去接任务”时，从同一看板选择任务；独立任务同样遵守认领、冲突检查、验收和关闭协议。

独立任务在文件头省略 `业务组` 与 `父账本` 两行，看板的业务组列显示 `—`；正文「问题来源」记录用户提出的现象或需求、已知复现信息与预期结果。业务组任务同时填写这两个字段并匹配现有章程。无需建立“杂项组”、占位章程或第二张看板；后续确认归属时可补关联，归组不阻塞执行。

## 职责与适用范围

- 主代理是本轮维护者：发布与调整 issue、确认认领、协调依赖、审核子代理交付、更新业务组结论。业务组负责问题方向，不永久占有涉及的代码模块。
- 业务组任务按 [当前职责裁定](../README.md#职责裁定) 指定唯一交付组和父章程，一组一文档，历史组不接受新任务；跨组交接合同与证据，不给同一根因另开重叠实现单。修改 Skill 等被测行为的任务不得同时改验收题目或 grader。
- 执行者负责一张 issue：读现场、实现或采证、自审、提交审核材料。发现在授权范围外的根因时交回维护者调整任务，禁止为了守文件清单而在错误层修补。
- 协调者串行处理认领及状态登记，执行者可以编辑自己已经获准的文件。共享工作区只有一个指定 Git 写者，默认主代理，负责按任务提交交付；未提交的登记属于有效协调状态，不得为了清理工作树而还原或随其他任务提交。
- 多会话共享工作区由用户指定一个协调会话，其主代理担任维护者；其他会话提交认领申请。不同 worktree / clone 的本地提交不构成互斥；未经维护者在协调工作区登记并确认，不得自主抢单。本协议不提供分布式锁。

## 状态与结果

| 状态 | 含义 | 文件位置 |
|---|---|---|
| 开放 | 合同已具备，尚无执行者 | 本目录和看板 |
| 认领 | 已确认执行者；包括调查、方案设计、实施、验证和等待审核 | 本目录和看板 |
| 阻塞 | 缺输入、环境、决策或依赖；正文写原因、解除条件、跟进者 | 本目录和看板 |
| 完成 | 完成条件已验收；与成果一起归档提交，提交成功才宣告交付 | 最终提交准备期间可在 archive |
| 取消 | 不再执行或已拆分替代，写明原因与替代 issue | archive |

常规流转：`开放 -> 认领 -> 完成 -> archive`；遇阻塞可从开放或认领转入，解除后由维护者恢复开放或原认领。等待审核仍保留认领和占用。取消必须由维护者确认。

**issue 完成与业务组验收通过分别记录。** 实现类必须满足行为与回归条件；证据类完成条件是约定范围的有效采证与判读，允许结果为 FAIL，但缺凭据、未执行、无效运行不能冒充完成。任何代码修改都须通过相关确定性回归，不能借证据类放行代码缺陷。组内阶段门在唯一父章程按全部证据裁定，不重复维护同一门槛。

## 发布 Issue

1. 任务来源可以是业务组未完成合同，也可以是用户直接提出的问题或需求。维护者按 [`_template.md`](_template.md) 写出一个可独立验收的结果；用户要求交给其他 Agent 的任务不必先归组。没有条件执行的已明确工作发布为阻塞；尚未定合同的组内方向留在章程，独立任务则保留待确认的问题和解除条件。
2. 写齐结果、修改范围、当前代码锚点、不变量、前置条件、并行限制、验证和完成条件。使用现有类型 `实现` 或 `证据`。多个结果如果依赖不同凭据、可分别验收，就拆开。
3. 任务包自足指无需从长章程推导本次任务。执行者仍须读取适用 AGENTS、当前实现、调用链、测试和 diff；合同冲突交给维护者裁定。
4. 发布前查所有组和独立任务是否已有重复或重叠工作；优先补充已有任务、关联依赖或安排等待，不重复开工。根因未知时记录真实现象和预期，授权有界调查；不得猜测根因或硬指定修复文件，调查后由维护者确认实际修改范围。
5. 写入同一看板并提交。依赖引用具体 issue 或章程条款及所需结果；仅有文件不重叠不能证明可并行。GitHub 产品 issue 若有关联，记链接即可，不复制其状态机，也不为本地独立任务强制创建 GitHub issue。

## 认领与并行

**任务所有权是任务级分析的前置条件。** 执行者（包括自行接单的主代理）必须完成认领，再开始读源码、追踪调用链、复现问题、分析根因、设计方案、运行测试或委派调查。只读分析同样属于任务工作，不得以“先看看怎么做”为由跳过认领。

认领前只读取仓库协作规则、看板和候选任务包，查看 Git 状态及已登记的前置、路径和资源占用，用于选单与冲突检查；不沿代码锚点展开调查。选定一个可申请的任务后，下一步立即申请认领，不先输出实现计划。没有合适任务时报告原因；等待确认、申请被拒或任务已被他人持有时，停止该任务的分析，不预研或囤积其他任务。

1. 执行者申请一个开放 issue，只需提供任务 ID 和可区分会话的认领者标识，无需先准备技术方案。维护者复读当前 issue、看板和 `git status --short`，检查已有改动的归属；一名执行者同一时刻仅占用一个 issue。
2. 检查所有尚有认领者的 issue：修改路径不能相交，写入也不能碰对方冻结输入。运行期间不得并发修改共享 provider 设置、暂停对方 worker、重建共享 DB 或覆盖同一采证目录。具体资源写进 issue 的「前置与并行」。共享文档由 Git 写者排队整合。
3. 维护者将状态改为 `认领`，用能区分会话的名字登记，例如 `主代理-<session短ID>` 或 `<session短ID>/eval-skills`，填带时区的 ISO 认领时间，即时同步看板并通知执行者。执行者复读协调工作树，核对状态为认领、认领者为自己、时间已填写且看板一致；维护者确认后即持有所有权，可以开始调查与方案设计，无需 Git 提交。口头申请、未经维护者确认的自行改字段或其他 worktree 的本地记录均不算取得所有权；主代理自行执行也须完成登记与复核。不得创建认领 commit。
4. 若一次 live 验证要求同 commit、干净工作树，使用独立固定 checkout，认领和证据登记留在协调工作树；共享运行资源仍需预约冻结窗口。不要为了满足 clean 要求提交或还原协调状态。所有复跑结束后再写证据；不得仅检查启动瞬间。

维护者为发布、冲突裁定或验收而进行的必要检查仍按其职责执行；若转为承担某张任务的调查或实现，同样先取得所有权。用户直接交办的非看板小修和只读调查继续按普通工作处理，不因此强制建单。

## 阻塞与交接

阻塞时在 issue 的「阻塞与交接」记录已完成部分、原因、解除条件、跟进者和现有 diff / 进程 / 冻结资源，即时同步看板，不单独提交状态记录。有未处理改动或仍在运行的资源时保留认领者，占用仍有效；执行者停止扩展实现。解除或释放时同样只更新协调记录。

维护者确认进程结束、环境恢复，且现有改动已明确移交或由原作者妥善处理后，才可清空认领者/认领于，释放占用。不得自动回滚或删除未提交改动。恢复认领前重新检查冲突。放弃但仍可执行的 issue 回到开放；会话失联不按时间自动抢占，由维护者完成同样的交接检查。

## 验收与关闭

1. 执行者完成约定验证，审自己的完整 diff（含未跟踪文件），在证据中写命令、结果、采证基线与已知缺口；issue 保持认领，提交审核材料给维护者。
2. 维护者审核任务合同和跨任务影响，写入审核者与结论。主代理自己执行时明确记录自审，不伪称独立审核；正常任务此时不提前提交实现。
3. 仅当任务合同明确要求固定候选 commit 做后续 live 验证时，允许候选实现与最终验收分两次提交，在任务中记录原因。候选实现须通过确定性回归和审核，提交后仍保持认领。按固定基线跑完全部 live 后审核证据；未满足完成条件时保持认领或阻塞，不关闭。
4. 条件满足后记录审核结论、issue 结果及适用的业务门槛结果，标完成。交付定位写“随本任务提交”，通过归档文件的 Git 历史定位；已有独立候选 commit 才填写其 hash，不为回填本次提交的 hash 再提交或 amend。业务组任务同步唯一父章程受影响条目的结论、剩余缺口及证据链接；独立任务在本文件记录结果。两类任务的稳定行为变化都按文档所有权更新活文档。跨组消费证据引用原 run_id/issue，不复制评分权。原始日志保留在产物目录，详细摘要留在 issue。
5. 将 issue 移入 archive、移除看板行、修正相对链接和所有旧链接，更新 [`archive/README.md`](archive/README.md) 索引。运行 `just docs-check`，复核整个任务 diff，将成果、测试、必要活文档、最终证据与归档合为一次交付提交；提交成功前不释放占用、不宣告交付。共享索引只暂存本任务变更，核对 `git diff --cached` 与 `git diff --cached --name-only`，不得夹带其他任务的未提交状态；不 push。提交失败时保留现场和占用，处理失败后继续，不假报完成。
6. 「完成后可拆」是后续发布建议。由维护者核对原始用户需求或组章程、依赖和既有 issue，条件成立才发布；执行者不自行连开后续任务，也不另提交例行归档或进度记录，交付后停下等分配。

证据类同样以本任务的有效证据、结论和归档形成一个交付提交。维护者确认取消时，取消理由、替代任务关联和归档作为一次终结处理，不拆出释放认领提交，也不写已交付。已存在认领或候选提交的任务保留历史，剩余成果与关闭记录合并提交，不重写已有提交。关闭后的 issue 保留历史结论，后续回归新建关联 issue，不覆写旧证据。
