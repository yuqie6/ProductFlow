# 内部 Issue 看板

本目录是仓库内的轻量 issue tracker。业务组维护方向与验收口径；每份任务文件是一张 issue；本页展示未关闭 issue；[`archive/`](archive/) 保存关闭记录。业务组与后续发布条件见 [`../README.md`](../README.md)。普通小修和只读调查无需建 issue。

**任务文件是状态与交付合同的权威，本表是同步索引。** 更新状态时同一提交修改两处，`just docs-check` 校验一致性。文件名是稳定 issue ID，关闭后仍可引用；不重复使用已归档 ID。

## 职责与适用范围

- 主代理是本轮维护者：发布与调整 issue、确认认领、协调依赖、审核子代理交付、更新业务组结论。业务组负责问题方向，不永久占有涉及的代码模块。
- 执行者负责一张 issue：读现场、实现或采证、自审、提交审核材料。发现在授权范围外的根因时交回维护者调整任务，禁止为了守文件清单而在错误层修补。
- 共享工作区只有一个指定 Git 写者，默认主代理。认领、状态变更、交付和归档提交都由该写者串行执行；执行者可以编辑自己已经获准的文件。
- 多会话共享工作区由用户指定一个协调会话，其主代理担任维护者；其他会话提交认领申请。不同 worktree / clone 的本地提交不构成互斥；未经维护者在协调工作区登记并确认，不得自主抢单。本协议不提供分布式锁。

## 状态与结果

| 状态 | 含义 | 文件位置 |
|---|---|---|
| 开放 | 合同已具备，尚无执行者 | 本目录和看板 |
| 认领 | 已确认执行者；包括实施、验证和等待审核 | 本目录和看板 |
| 阻塞 | 缺输入、环境、决策或依赖；正文写原因、解除条件、跟进者 | 本目录和看板 |
| 完成 | issue 的完成条件已验收、交付已提交 | 归档前留看板，关闭后进入 archive |
| 取消 | 不再执行或已拆分替代，写明原因与替代 issue | archive |

常规流转：`开放 -> 认领 -> 完成 -> archive`；遇阻塞可从开放或认领转入，解除后由维护者恢复开放或原认领。等待审核仍保留认领和占用。取消必须由维护者确认。

**issue 完成与业务组验收通过分别记录。** 实现类必须满足行为与回归条件；证据类完成条件是约定范围的有效采证与判读，允许结果为 FAIL，但缺凭据、未执行、无效运行不能冒充完成。任何代码修改都须通过相关确定性回归，不能借证据类放行代码缺陷。阶段门只在父章程中按全部证据裁定。

## 发布 Issue

1. 维护者从业务组未完成合同或已确认缺口拆出一个可独立验收的结果，按 [`_template.md`](_template.md) 写 issue。没有条件立即执行的已明确工作发布为阻塞；尚未定合同的方向留在业务组后续发布条件中。
2. 写齐结果、修改范围、当前代码锚点、不变量、前置条件、并行限制、验证和完成条件。使用现有类型 `实现` 或 `证据`。多个结果如果依赖不同凭据、可分别验收，就拆开。
3. 任务包自足指无需从长章程推导本次任务。执行者仍须读取适用 AGENTS、当前实现、调用链、测试和 diff；合同冲突交给维护者裁定。
4. 写入看板并提交。跨组依赖引用具体 issue 或章程条款及所需结果；仅有文件不重叠不能证明可并行。GitHub 产品 issue 若有关联，记链接即可，不复制其状态机。

## 认领与并行

1. 执行者申请一个开放 issue。维护者复读当前 issue、看板和 `git status --short`，检查已有改动的归属；一名执行者同一时刻仅占用一个 issue。
2. 检查所有尚有认领者的 issue：修改路径不能相交，写入也不能碰对方冻结输入。运行期间不得并发修改共享 provider 设置、暂停对方 worker、重建共享 DB 或覆盖同一采证目录。具体资源写进 issue 的「前置与并行」。共享文档由 Git 写者排队整合。
3. 用能区分会话的名字登记，例如 `主代理-<session短ID>` 或 `<session短ID>/eval-skills`，填带时区的 ISO 认领时间。同步看板，提交 `chore: 认领 tasks/<ID>`；提交成功并通知执行者后才能开工。
4. 若一次 live 验证要求同 commit、干净工作树，安排独立固定 checkout，或预约整段共享工作区冻结窗口。窗口内连其他任务的认领、证据和归档提交也暂停。所有复跑结束后再写证据；不得仅检查启动瞬间。

## 阻塞与交接

阻塞时在 issue 的「阻塞与交接」记录已完成部分、原因、解除条件、跟进者和现有 diff / 进程 / 冻结资源，同步看板并提交状态记录。有未处理改动或仍在运行的资源时保留认领者，占用仍有效；执行者停止扩展实现。

维护者确认进程结束、环境恢复，且现有改动已明确移交或由原作者妥善处理后，才可清空认领者/认领于，释放占用。不得自动回滚或删除未提交改动。恢复认领前重新检查冲突。放弃但仍可执行的 issue 回到开放；会话失联不按时间自动抢占，由维护者完成同样的交接检查。

## 验收与关闭

1. 执行者完成约定验证，审自己的完整 diff（含未跟踪文件），在证据中写命令、结果、采证基线与已知缺口；issue 保持认领，提交审核材料给维护者。
2. 维护者审核任务合同和跨任务影响，写入审核者与结论。主代理自己执行时明确记录自审，不伪称独立审核。Git 写者只暂存已审的本任务文件，检查 `git diff --cached --name-only` 后提交交付；不 push。
3. 必须在提交后执行的 live 验证可先提交通过确定性回归的候选实现，issue 仍是认领，提交不代表验收完成。按固定基线跑完全部 live 后审核证据；未满足实现类完成条件时保持认领或阻塞，不关闭。
4. 条件满足后记录交付 commit、审核结论、issue 结果和业务门槛结果，标完成；维护者同步父章程受影响条目的结论、剩余缺口及证据链接。原始日志保留在产物目录，详细摘要留在 issue。不能只改父章程的任务指针。
5. Git 写者将 issue 移入 archive、移除看板行、修正移入文件的相对链接和所有旧链接，更新 [`archive/README.md`](archive/README.md) 索引。取消也走此关闭步骤，但不得写已交付。
6. 「完成后可拆」是后续发布建议。由维护者核对当前章程、依赖和既有 issue，条件成立才发布；执行者不自行连开后续任务。运行 `just docs-check`，提交关闭记录，然后执行者停下等分配。

证据类没有代码交付时，审核、完成和归档可合为一个关闭提交；实现类保留独立代码提交。关闭后的 issue 保留历史结论，后续回归新建关联 issue，不覆写旧证据。
