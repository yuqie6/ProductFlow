# Agent 自进化组

本组交付一个在既定目标、权限、数据和预算内自动发现失败、检验根因假设、产生修改、验证和迭代的系统。业务目标是帮助商家准确整理资料、修改工作流和执行任务，减少错误目标、遗漏约束、无用往返和未确认副作用。正常路径只在最终进化版本提交给用户时审批一次。改进对象覆盖影响 Agent 任务成效的指令、工具、Node 适配和必要 Go / Web 实现；模型权重训练不在当前合同。

2026-09-05 用户确认按完整结果重划业务组。本文件替换旧 Self-Harness P3–P7 与后加 S0–S6 的未来路线；P1/P2/P2b 的实现和历史归档保留。旧的 Prompt-only、每簇人工抽读、逐阶段人工交接、Steer/记忆作为发布前置均不再适用。当前没有自动进化控制器，以下目标不得写成已实现。

## 本期目标与范围

2026-09-08 产品目标与权限边界校准为 [可自托管多商家 SaaS](../ROADMAP.md)。普通账号只对应一个自有 Merchant；目标合同允许平台管理员在明确的 `merchant_id` 上管理所有商家的已有商品，管理不改变商品归属。下述单商家实验范围是固定开发基线，不代表最终产品定位。自进化控制器仍按既有完整结果交付，不等待真实商户、生产回流或多商家全量改造；未来消费新商家合同前，独立冻结授权与评测输入。候选不能自行修改租户隔离、消费边界、评分或最终审批规则，也不能以工作区或商家切换、团队角色或支持会话替代这些边界。

2026-09-05 设计收敛：本期面向当前单管理员、单商家 ProductFlow，在一个事前固定的生产模型组合和业务版本上验证自动改进。通用 harness、跨模型泛化、开放式满意度归因与长期偏好学习保留为未来问题，不增加本期启动或验收门槛。完整自动选题、指令/代码修改、有界多轮验证及最终一次审批仍是交付目标。

| 维度 | 本期选择 | 结果适用范围 |
|---|---|---|
| 任务 | 资料整理、工作流修改、运行及失败处理等有明确业务后置条件的任务 | Agent 行为改善；成图审美与实际图片可用性由图片质量合同另行判断 |
| 初始数据 | 获准且可测的冻结开发包，含成功、失败、输入和真实工具观察 | 不要求生产反馈、满意度标签或长期用户画像先就绪 |
| 模型 | 固定 provider/model、请求配置及参与本次任务的其他模型配置 | 改善属于该模型、harness、工具和任务组合；不外推为跨模型质量保证 |
| 修改 | 在批准范围内按一个因果假设修改 Skill、领域壳或必要业务代码 | 不限于提示词；权限、评分、预算及生产迁移不由候选修改 |
| 搜索 | 单个当前最佳父版本、串行候选、外部固定验证 | 保留无改善结论；不承诺每轮产生补丁或持续加速 |
| 交付 | 已集成并完成相应验收的精确候选及证据，最终一次用户审批 | 可运行、有效改进和长期业务收益分别说明 |

本期业务评测优先覆盖首次套图、指定修改、选定下载和下一商品复用。批量及更宽的多商品自动化属于独立扩展，不作为小范围试用、开发基线或自进化启动的硬前置。

控制器、隔离和预算属于工程交付；自动诊断是否有效、改进能否在未参与搜索的任务上复现，需要实验举证。一次修复案例不能证明持续收益，开发分数上升不能代替独立验收。保持原有质量、安全和晋升合同，不因范围收敛降低数值门槛。

## 交付范围

- 本组拥有自动改进流程的端到端交付：固定输入、隔离实验、失败挖掘、候选生成、可信验证、迭代记录、停止与最终审批交付。必要的测试适配纳入本组任务序列，复用公共实现，不等待其它组逐轮接单。
- 普通人工工程修复由 [Agent 质量组](agent-eval-system.md) 承接。[eval-skills](tasks/eval-skills.md) 的人工候选与结果不算本系统的自动收益。
- 每轮使用已发布的固定评测与业务合同。评测器在候选之外运行，候选不能修改其规则、隐藏材料或成绩；独立验证不要求另一个工作组人工运行。
- 已知普通生产故障继续正常修复，不为保存实验基线留在线上；自动进化在固定隔离版本中进行。共享代码变更仍由协调者预约排他范围，组不永久占有模块。
- 现有 [eval-development-baseline](tasks/eval-development-baseline.md) 是一次性启动输入任务，三批采证均未形成有效完整开发包。[不可测消费边界](tasks/archive/eval-unobservable-trial-boundary.md) 与 [图观察权威](tasks/archive/eval-graph-observation-authority.md) 已交付；新冻结批次仍待开发基线采证。前置与占用以对应任务为准。它不定义未来每轮的人工流程。

## 组件与复用边界

商家任务继续走现有 Pi 与 ProductFlow 业务后端。自进化在固定版本的隔离副本上运行，首期提供一个离线编排入口；不为实验另建商家对话产品或通用 Agent 框架。

| 部分 | 本期职责与输入输出 | 写入边界 |
|---|---|---|
| Pi 与领域壳 | 复用模型 loop、工具接入、会话和上下文能力；用候选代码运行相同业务任务 | 实验实例只操作隔离业务环境，生产实例保持当前版本 |
| 进化控制器 | 读取冻结配置，组织选题、提案、构建、评测与停止；记录候选谱系、尝试和费用 | 写实验记录；候选不能改其预算、接受规则或评分入口 |
| 提案 Agent 与编码执行器 | 读取获准开发证据、源码和历史拒绝原因；输出根因假设、补丁、预测效果和回归检查 | 只写候选工作区；不能读取隐藏验收材料、生产资源或发布凭据 |
| 可信验证程序 | 复用公共评测与真实 Go 业务路径，读取业务后置条件和外部调用记录；输出完整结果与接受/拒绝依据 | 评分和正式证据由候选之外的执行方持有；候选测试只能提供辅助证据 |
| 最终交付入口 | 整合目标版本的候选、验收与恢复说明；接收绑定精确版本的用户决定 | 批准前不改生产；使用现有构建部署流程执行已批准的版本 |

这些是职责和访问边界，不要求五个服务、五个 Agent 或新建五套持久化。实验产物使用一个受控目录及不同访问权限；具体内部类型与入口在对应实现任务确定，不提前增加生产表、HTTP API 或通用插件协议。

生产底座继续使用 Pi。编码执行器优先验证现有 Pi 能力是否满足限定补丁、构建和产物采集；只有出现具体缺口才评估 OpenHands 等替代接入，不把多框架选型比较设为必经步骤。GEPA、Harbor 等只在对应搜索或隔离验证能力有实际收益时接入，不能替代 ProductFlow 的业务评分与权限权威。工具、会话和上下文等通用能力优先复用上游；领域工具和可验证业务结果由本项目维护。

## 正常运行合同

```text
已冻结的目标 / 模型配置 / 权限 / 预算 / 数据与评测版本
  → 重放有效任务，核对观察与真实失败
  → 自动选择问题，提出并检验根因假设
  → 隔离生成指令或代码候选
  → 自动回归、比较、拒绝或迭代
  → 将最终候选集成到目标版本，冻结后独立验收
  → 用户一次最终审批
  → 按批准版本发布并记录结果
```

1. 自动选题须区分事实与假设。缺少必要用户目标或工具结果时记录证据不足；不能把所有失败归因到 Skill。初版直接分析有界开发轨迹即可，封闭分类词表、聚类平台和单独 Miner 服务不作为前置。
2. 同一轮内部接受的候选只更新隔离实验父版本，不修改生产。保留失败尝试、修订和成本；预算内可以继续尝试，达到停止条件输出完整结果。
3. 最终审批前自动完成版本冻结、独立验证和报告。用户看到改了什么、为什么、比较结果、回归/副作用风险、总成本与恢复方式；批准绑定精确工件，不是允许下一轮任意改动。
4. 没有合格候选、预算耗尽、输入不可信或越出授权范围时自动停止，不把人工选题、诊断、逐候选审批或手修补丁当正常兜底。系统报告阻塞或无改善，不能伪造成功。
5. 已设定的权限、费用限额和有效数据是运行配置。未配置则不可启动；运行中不能提高自己的权限或预算。人工标签校准等基础材料建设单独记录，不伪称每轮不需要人就等于不需要任何可信输入。
6. 批准后由已有构建/发布方式应用该精确版本，无第二次例行人工发布确认；内容、依赖或有效配置变化即不再沿用原批准。审批与发布接口尚未实现，不能将此条理解为当前自动部署授权。

## 一条组内交付序列

以下三项是发布任务的结果边界，尚未同时发布为 issue。先完成前项的可执行交付，再发布下一项，不设并行的第二套阶段表。

| 顺序 | 可独立验收的结果 | 必要证据 |
|---|---|---|
| 固定实验与自动验证 | 同一固定业务和模型版本可以在隔离环境重放有效问题、构建候选并调用固定验证；系统拒绝篡改评分和凭据访问 | 固定代码/数据/评测身份、父版本真实失败、环境重建与隔离测试；完整尝试及预算记录，拒绝不可测输入；必要适配在本组建设 |
| 自动发现到改进 | 从获准执行记录自动选题、诊断、产生修改并完成候选验证；包含一条真实代码级问题，不能全部只改 Prompt | 记录中无人挑题、手写诊断或补丁；自动候选修复父版本失败，相关合同与安全回归通过；明确一次案例不能证明普遍收益 |
| 多轮与最终审批 | 有界多轮运行，失败不丢弃，正常路径只在最终版本审批一次；批准、拒绝、取消、无改善、超预算和版本漂移均可验收 | 多个问题上的成本与效果、独立验收、完整谱系、一次批准应用精确版本及恢复演练 |

初始开发输入须消费已交付的 [图观察权威](tasks/archive/eval-graph-observation-authority.md) 等测量修复，再由 [开发基线](tasks/eval-development-baseline.md) 冻结用途清单、完整采证并导出。取得开发包后本组自行编排，不等待 Agent 质量组全部 L0–L6、nightly 或日常候选完成。真实隐藏材料缺失时可以验证已有开发范围，不能跳过最终独立验收；需要语义裁判的实验仍须满足其校准合同。

组内后续可建设当前缺失的验证入口与受限部署，调用已有公共评测实现。涉及被测行为与评测合同的工作分成先后任务，分别审核并冻结；修改候选时正式评分不变。

## 修改权限与最小实现

一个候选验证一个因果假设，必要时跨层。工具参数/结果、Graph 业务实现、事务、状态查询与必要前端投影均可在事前批准范围内提出代码补丁。权限/确认语义、评分权威、生产迁移、凭据和发布授权不由候选修改；新工具或合同变更超出当前范围时自动拒绝该提案，不临时向用户追加审批步骤。

首期离线编排复用编码执行器、Git 补丁和现有评测产物，不另建任务板、通用版本中心或生产 shell 工具。领域壳工件继续沿用已交付装配；普通 Skill/代码候选通过固定 checkout 和构建验证，不为了表示一次候选引入运行中 overlay 热切。

- 编码和构建环境不持生产 DB/storage、共享 .env、SSH/Git 凭据或宿主 Docker socket。安装脚本与测试同样是不可信执行；模型调用和资源受外部预算控制。
- verifier 与隐藏材料独立于候选执行环境；独立读取业务后置条件和外部调用记录，不能只信候选自报成功。后端问题使用真实隔离 PG 及相关故障测试，替身结果不代替真实 provider 结论。
- 问题包保留必要事实与引用关系，缺失明确标记。每次实验关联代码/构建/依赖、harness/Skill、模型请求选项、任务/数据、verifier、控制器和环境版本。复用已有记录，不新增多个身份注册表。
- 成本记录全部模型与评测尝试、人工审查时间和无法取得的 usage；上限从可信配置读取，不由候选提高。不为跑到成功增加次数或丢掉失败项。
- 代码发布走正常构建部署，不通过 harness_hash 热替换 Node/Go。代码恢复与已发生数据/付费副作用分别处理；首期生产迁移不自动执行。
- 线上既有 Turn 和 WorkflowRun 的在途行为按相关合同验证；确实需要时采用维护/排空窗口，不引入仓库已禁止的双运行时或旧数据迁移路径。

## 首期控制算法与工程约束

以下为未实现的首期设计，依据本页研究记录收敛；不增加业务组、常驻服务或并行阶段表。控制器保存运行进度，提案 Agent 负责诊断与修改，可信验证程序决定成绩和接受结果。进程内函数分工不提供安全隔离；候选执行与可信验证仍须具有不同写权和凭据。

### 证据与自动选题

开发实验复用已导出的任务与试验身份，保存以下最小材料。它们是实验目录的内容合同，不是新增生产数据模型；日志、转录和补丁留在隔离产物目录，章程只引用证据。

| 材料 | 必需内容 | 用途 |
|---|---|---|
| 实验配置 | 原始基线、目标版本、代码/依赖与壳/Skill 身份、模型角色及请求配置、集合用途、verifier 身份、修改范围、预算和停止条件 | 启动前冻结，恢复时核对；具体值由实验任务登记 |
| 开发证据索引 | task/trial 引用、当时目标与可见事实、实际工具参数/观察、后置条件、测量有效性、成功失败记录 | 提案 Agent 只读检索，不把摘要当完整事实 |
| 候选与尝试 | 父候选、假设与证据位置、补丁、预测改变、验证结果、拒绝原因、全部模型调用与费用 | 每次尝试都留存，防止只展示胜出候选或重复抽样 |
| 最终交付材料 | 原始基线与最终实验候选的对照、目标版本集成验收、范围和未知项、累计费用、恢复方法、绑定版本的批准/拒绝结果 | 支持最终一次审批，区分实验收益与发布资格 |

提案 Agent 按需读取脱敏开发文件及索引。失败和成功对照都保留，隐藏验收原文、凭据和未授权商家材料不进入可读目录。无需向单次模型上下文塞入全部历史，也不建设向量库或另一个知识平台。

当前 `src/evolution-traces.ts` 的有界尽力记录只能提供诊断线索；截断、丢失或缺少用户目标时，控制器在获准的隔离开发环境补跑并采集必要证据。不能将现有线上 trace 扩成无限全量日志，或把缺失内容当作模型未观察到的事实。

选题从 verifier 确认的失败开始，按业务影响、不同任务上的支持证据和授权范围内的可验证性排序；同一任务重复试验不冒充多个独立问题。模型给出的根因保留为假设，并提交证据位置、预测改变的行为和可推翻该解释的检查。确定性问题要求父版本失败、候选通过；随机模型行为按后述配对实验判断。证据不足时自动补证或跳过，不插入人工挑题步骤，也不靠聚类标签证明因果。

### 反馈如何进入实验

首期自动选题来自可测开发证据，不要求建设线上投诉归因或用户画像。用户不满意、撤销、重生成以及 judge 低分只能提供线索；不能直接证明 Agent 错误或授予修改全局 Skill 的资格。当线索涉及某次任务时，按 [测量有效性合同](agent-eval-system.md#测量有效性与失败归因) 核对执行时已经表达的要求、当时可见事实、实际参数、工具反馈与后置条件。

| 证据情况 | 本期处理 |
|---|---|
| 已明确只改第二张，却实际改动共享方案或其他对象 | 在隔离环境重放并验证偏差；按根因提出行为或业务代码候选 |
| 生成输入符合要求，某次图片仍失真或不符合审美 | 不能直接判为 Agent 失败；成图问题按图片质量合同处理，不以一次重生成变好证明 harness 改善 |
| 用户看到结果后新增偏好，或改变原要求 | 沿当前任务调整要求；不倒推原执行错误，不自动写长期偏好或全局策略 |
| 输入缺少必要素材或信息 | 先核对 Agent 当时能否识别缺口、是否有必要澄清；只有存在明确遗漏或虚假承诺的证据才成为行为候选 |
| 工具反馈缺失、结果 unknown、评分期望与真实业务不符 | 保留诊断，禁止能力比较和候选接受；按既有测量修订流程处理，不能在候选中修改正式评分 |

这张表用于限制证据解释，不要求开发通用反馈分类器。事实无法判定时可在冻结预算内补证；仍不可判定就跳过或结束。外部模型失败不自动免除 Agent 在必要澄清、正确传参和如实报告上的责任，但每项责任须有当时合同与观察支持。

商家当前任务的继续修改与全局候选选择分别处理。满意度、撤销率或重生成次数不单独作为优化目标；沿用固定完成条件和负例检查，避免通过少执行、多追问或一律拒绝取得表面改善。开放式偏好归因不纳入本期验收。

### 固定模型与证据范围

生产任务模型、提案模型及语义 grader 模型分角色记录；未使用语义 grader 时不新增模型调用。首期沿用同模型研究基线；具体 provider/model、推理参数和调用预算由实验配置冻结，不在章程指定永久型号。开发助手编写控制器的能力不等于被测生产模型的能力，也不计作自动收益。

对照时固定参与链路的模型和实际可取得的请求配置。供应商执行参数或用量无法核实时明确记未知，不能只凭声明的模型名声称等价。除候选声明的补丁外，中途切换模型、关键配置或业务版本使该比较失效；新组合重新建立基线，不沿用旧候选的接受或发布资格。首期不要求多模型矩阵、模型专属 harness 分支或迁移实验；模型特化可以是本期有效结果，但结论必须写明适用组合。

### 候选与停止

首期采用单个当前最佳父版本的串行搜索。每次只验证一个因果假设，允许必要跨层补丁；候选数、每题尝试次数、连续无改善轮数、总时限和费用在启动前固定。未通过的候选及拒绝原因仍进入记录，供下一次提案避开已失败尝试；通过固定筛选规则才成为新的实验父版本。候选重复时复用已有证据，不凭重复提交获得额外样本。

暂不实现种群、岛屿、跨候选自动合并或多优化器路由。只有在同预算对照中证明单父版本搜索确实受限，才测试候选档案分叉或 GEPA 的选择策略。没有改善可以正常结束，不能沿用参考实现中强制每轮产出候选的提示来掩盖证据不足。

### 验证与预算

候选依次接受构建/针对性回归、冻结开发与回归集筛选、最终独立验收。廉价失败提前拒绝以节省付费调用；候选新增的测试可作为修复证据，但正式成绩由固定 verifier 和受保护回归给出。基础设施故障与任务失败分别记录，重试次数固定且计费，不通过删除失败样本改善成绩。

随机任务在相同任务、环境与请求配置下配对比较父版本和候选，并平衡运行顺序。按任务汇总重复试验，报告差值、不确定区间及成本；固定 k 次运行不自动等于统计显著。需要置信推断时，在实验启动前写明统计方法、样本量和停止规则，不能看到上涨才选择停止。最终验收失败就结束本次实验，不将其案例或详细反馈回流到本次搜索；已用来选版本的材料后续不能继续声称未见。

逐轮通过只授予下一轮实验父版本资格。最终对照保留本次原始基线，累计检查全部修改对业务、负例和成本的影响，不能只和最后一轮父版本比较而掩盖累积退化。代码缺陷以真实旧版失败/新版通过及受影响回归证明修复；模型行为收益由冻结的重复试验判断，二者在报告中分别列出。

缓存只复用身份完全一致的已完成试验。实验身份包含代码/依赖、数据集合、verifier、模型/请求配置、环境和试验编号；变更任一项须隔离缓存。缓存命中不增加独立样本数，随机复验必须有新的试验编号。GEPA 当前不同缓存层的键不自动覆盖以上身份，接入时不能直接把其磁盘缓存当作跨实验真相。

费用上限覆盖诊断、提案、候选执行、失败重试和最终验收。开始搜索前预留最终验收额度；外部调用发出前由可信执行入口登记尝试并预占额度，结束后核对 usage，未知用量保留为未知且不释放预占。框架的评测次数、提案 token 预算与最终报告相加不能代替总费用硬约束。首期串行执行避免并发预占复杂度，但仍须验证超时和崩溃路径。

### 恢复与最终审批

复用实验产物目录记录父候选、已完成验证、在途尝试及费用，不新增生产业务状态机。恢复时核对冻结身份，复用已完成试验；调用已发出但结果未知时，使用已有外部请求标识核对，不能假定未生效并自动重发。无法核对则停止该实验并保留未知成本，允许失败结束，不以人工查账作为正常进化步骤。至少验证调用前、调用后未记结果、结果已落盘三处中断，以及预算不会因重启清零。

提交用户审批前，自动将候选应用到实际目标版本并完成相关构建、回归与独立验收；主线漂移或冲突形成新候选，旧实验通过不覆盖新组合。若目标版本已变，集成对照使用该目标版本的未打补丁版本；原始实验对照单独保留。批准绑定最终代码、构建、依赖和有效配置身份，发布入口核对实际目标版本。审批后发生身份漂移即拒绝应用并结束本次交付，不静默重算后沿用旧批准；后续新版本属于新实验。最终报告必须区分原冻结版本上的研究收益与集成版本上的验收结果。

## 验证与出口

当前 G1 = 完整自动进化后一次最终人工审批；状态为缺失。原 G2 的无人工晋升不在本期交付目标，不作为“自进化完成”的必要条件。

[Agent 质量测量合同](agent-eval-system.md#self-harness-评测用途)定义集合和评分语义，控制器自动执行固定版本。开发反馈与用于筛选的隐藏回归均不等于最终独立验收；暴露后的材料不能继续当作未见数据。合并或更新父版本形成新候选并重验。

既有纯指令实验的初筛门槛保留：双方 k=3；开发/隐藏回归均不降且至少一项提高，净增至少两个任务·试验；中位 tokens 增幅不超过 15%；指令总量不超过 16 KiB、overlay 不超过 10 KiB；负例不劣化且任何越权/未确认副作用直接拒绝。这些是筛选条件，不证明统计显著性，不将文本字节限制套到 Go 补丁。

代码级实验在开始前固定主要业务指标、成本限额、回归边界、样本量与停止规则，外部 verifier 按该规则运行。父版本失败、候选通过的确定性回归证明修复；在未见场景上的配对运行证明效果范围。保留不确定区间与无改善结论。未校准材料只能用于诊断，不能用最终人工批准豁免缺失的安全或有效性证据。

最终生产批准还须具备该修改面相关的执行可靠性和安全证据。涉及模型行为时引用有效的 D-08 与 L5 证据，不能拿历史版本 run_id 放行新版本；现有产品通过率门槛不因改组降低。G1 完成记录同时包含自动化程度、效果、成本和一次审批证据，不能只填“测试通过”。

以下情形用于核对本期规则，不增加另一套评分器或数值门槛：

| 验收情形 | 应有结果 |
|---|---|
| 系统自行从有效失败记录选题，旧版可复现，补丁通过固定回归 | 形成自动改进证据；仍须最终独立验收才能晋升 |
| 开发者指定具体失败并手写诊断或补丁 | 可以验证执行器与工程流程；不计为自动发现到改进的完成证据 |
| 用户仅说不好看，或新增原任务没有的偏好 | 不直接进入全局候选接受；无需等待高级反馈系统才能运行其他有效问题 |
| 原模型组合改善，其他模型未测 | 只报告固定组合效果；跨模型未测不阻塞本期该组合的验收 |
| 改题、缺失观察、模型漂移或只拿候选新增测试自证 | 拒绝将该成绩用于接受；修复测量时独立冻结新输入 |
| 没有改善、预算耗尽或付费调用结果无法核对 | 正常停止并保留全部尝试与未知费用；不能假报改进成功 |
| 最终独立验收失败，或批准后目标身份变化 | 停止该候选交付；不能用人工批准豁免或静默替换版本 |

## 收益归因与暂停条件

人工工程 A→B 与自动改进 A→C 分别报告；从更新后的 B 启动要明确新起点。无需等人工 B 完成才能建设控制器，也不刻意保留生产 Bug。系统级与 Prompt-only 对照固定共同父版本、生产/提案模型、评测规则和总预算；使用更强外部编码模型单列，不冒充同模型 Self-Harness 效果。

同模型自动挖掘、提案与验证循环是首期研究基线。问题输入来自系统自动选择的开发证据；当前外部编码助手搭建控制器属于工程建设，不计作该系统自动进化。

没有稳定收益时停止扩大投入，检查数据、搜索或修改面的真实瓶颈。Steer、长期记忆、复杂种群、自动合并策略、无人工发布与元进化均按具体证据另行立项，不挂成当前完成条件。自动挖掘、提案、验证与停止保留为核心要求。

## 未来问题

以下议题仅保留后续研究入口，不要求本期建设相应组件、采集额外数据或增加验收矩阵。

| 议题 | 何时值得重新评估 | 届时需要回答的问题 |
|---|---|---|
| 跨模型泛化与特化策略 | 产品实际需要支持多个模型组合或更换模型 | 同一原 harness 与候选在每个模型上分别对照；参与调优的模型与未参与的模型区分，不能用平均分隐藏退化 |
| 主观反馈与长期偏好 | 当前任务调整已经不足以满足真实商家需求，且有获准样本 | 当时需求、事后偏好、素材不足与生成波动如何区分；个体偏好何时可复用，何时不得上升为全局规则 |
| 通用 harness 或执行器替换 | 现有 Pi 的具体缺口已有复现，候选上游能减少维护或改善实测效果 | 接入兼容与行为质量分别验证，保留 ProductFlow 的业务和权限权威；不为追逐框架重建生产 loop |
| 长期收益与更复杂搜索 | 已有多批有界实验，并能定位单父版本搜索或成本的瓶颈 | 与人工改进比较完整成本和人力，检查多轮收益、组合退化；再决定是否引入分叉搜索、长期记忆或元进化 |
